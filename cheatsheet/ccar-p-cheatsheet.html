Core exam logic

  1. Simplest pattern that works. Workflow → agent → multi-agent, only on evidence.
  2. Remove capability before you guard it. Least privilege beats logging.
  3. Enforce in code, not the prompt. Permissions, hooks, schemas, validators.
  4. Static first, then cache. Batch what can wait.
  5. Diagnose from what changed. Match the trigger to the layer.
  6. Evals gate every change. Measured criteria, cost per task.
  7. Design for the handoff. Cost, risk, reversal; runbooks, owners.
How items are written: a production scenario → a trigger in the stem ("only ever need", "after a document refresh", "same prompt every request") → "best reduces risk" / "most directly addresses" / "first place to investigate" → four options. Pick the structural fix that matches the trigger and keeps the needed capability.

D1

Solution Design & Architecture

17% · ~11 items · Lesson 01
Objectives
  1. Translate business problems into Claude-based AI solutions
  2. Design end-to-end architectures (input → processing → output → feedback loops)
  3. Select patterns (workflow, agentic, augmented LLM)
  4. Design multi-agent systems and orchestration
  5. Apply decomposition techniques
  6. Align to value pillars (efficiency, transformation, productivity, cost, performance SLAs)

Four decisions before code, in order

  1. Ownership: Claude vs. existing systems vs. humans
  2. Shape: augment (live, seconds) · automate (pipeline) · agent (open-ended)
  3. Reference architecture: name the pattern
  4. Entry point: model, context strategy, surface, route

Lens: systems own exact figures, live facts, and state · code owns control flow · humans own consequential decisions.

The ladder: climb only on evidence

RungDefinitionCost
Augmented LLMOne call + retrieval, tools, memoryLeast flexible
WorkflowPredefined code pathsNo adaptation
AgentLLM directs its own steps in a loopLatency, tokens, compounding errors
Multi-agentOrchestrator + subagents~15× chat tokens (agents ~4×)

Flowchart drawable in advance → workflow. Agents need ground truth per step, stop conditions, sandbox.

Five workflows

PatternUse when
Prompt chainingFixed sequential steps; gates between
RoutingDistinct input categories (easy → small model)
ParallelizationSectioning (independent parts) or voting
Orchestrator-workersSubtasks unknown until input seen
Evaluator-optimizerClear rubric; iteration helps

Multi-agent rules

  • Beat single agent by 90.2% on Anthropic's research eval
  • Fits: breadth-first, parallel, info exceeds one context
  • Fails: tightly coupled work (most coding), shared context, real-time coordination
  • Subagents don't inherit context. Pass task, constraints, format
  • Scope tools per subagent; clear boundaries; orchestrator synthesizes

Decomposition and reference architectures

  • Pipeline (stages) · map-reduce (partitions) · local + integration pass (big reviews) · specialist · plan-then-execute
  • Docs Q&A → RAG · live state → tool call to system of record · bulk extraction → batch pipeline + structured outputs · support with actions → least-privilege agent + approvals · broad research → orchestrator-workers

End-to-end and value

  • Input (screening) → processing (pattern, model, context) → output (validation) → feedback loop (corrections → eval set → next version)
  • No feedback loop = can't improve or detect drift
  • Pillars: efficiency · transformation · productivity · cost · performance SLAs. Name the pillar and its metric first
  • Traps: agent for known steps · multi-agent for coupled work · RAG for live data
D2

Models, Prompting & Context Engineering

13% · ~8 items · Lesson 02
Objectives
  1. Select Claude models based on trade-offs
  2. Design system prompts, templates, guardrails
  3. Apply zero-shot, few-shot, chain-of-thought
  4. Optimize context windows and token usage
  5. Prompt reuse: caching, modular prompts, Skills

Model choice (lineup as of Oct 2026)

ModelFit$/MTok in · out
Fable 5.1Hardest reasoning, long-horizon agents10 · 50
Opus 5.5Agentic coding, knowledge work; "start here"4 · 20
Sonnet 5.5Speed + intelligence2 · 10
Haiku 5.5Classify, extract, route at volume0.10 · 0.50

Decide on your eval set. Tune effort before switching models. Route by difficulty. Compare cost per completed task.

Prompt caching

  • Order tools → system → messages, static → dynamic. Exact-prefix match
  • Up to 4 breakpoints; min 512 tokens on current models
  • TTL 5 min (write 1.25×) or 1 h (write 2×); reads a fraction of base input
  • Cache reads don't count toward ITPM on most models
  • Killers: timestamp/user ID at the top, changed tools, changing effort

Techniques and guardrails

  • Few-shot: 3–5 diverse examples in tags for exact format/mapping
  • CoT: higher effort or reasoning before the answer; arithmetic to a tool
  • Shape guarantee: structured outputs / strict tool use. Prefill and forced tool_choice error on new models
  • System prompt = role, scope, tone, "say I don't know." Not: hard limits, authz, secrets

Context engineering

  • Smallest set of high-signal tokens; 1M window ≠ use it all
  • Long doc: document first, question last, quotes before answer
  • Long sessions: context editing, compaction, memory tool, facts block
  • KB < ~200k tokens: all in context + cache
  • Skills: ~100 tokens metadata each; body and files load on demand

API MCP connector: tool calls only, public remote servers, not ZDR-eligible.

Observability and reliability

  • Log: request ID, model, prompt version, tokens incl. cache, latency, stop_reason, tool calls + args, chunk IDs. Redact PII. One trace ID across agents
  • stop_reason: "refusal" arrives as HTTP 200: instrument separately, set fallback per request
  • 429: honor retry-after, ramp gradually · spend-cap 429: no retry-after, alert · 529 overloaded: backoff/fallback
  • Patterns: retries · fallbacks · circuit breakers

Accuracy-latency and delivery routes

  • Levers: caching (TTFT) · fewer reranked chunks · lower effort · faster model on easy routes · parallel tools · streaming (perceived only). Justify with eval numbers
  • Claude API: full features, inference_geo: "us" · Platform on AWS · Bedrock (GovCloud FedRAMP High; some features missing) · Vertex AI (FedRAMP High) · Foundry
  • Procurement, residency, FedRAMP rule routes out before latency or cost

D3 traps

Logging instead of removing tools · "only access the user's records" in the prompt · vectors for IDs, aggregates, or live state · MCP for a single fixed call · final-answer-only logs · retrying a spend-cap 429 forever · streaming as an SLA fix.

D4

Evaluation, Testing & Optimization

16% · ~10 items · Lesson 04
Objectives
  1. Define metrics (accuracy, latency, cost, safety, security)
  2. Design datasets and mixed-method test frameworks
  3. A/B testing and iteration
  4. Diagnose prompt failure, hallucination, model mismatch
  5. Optimize tokens, latency, cost-performance
  6. Monitor with logging and observability

Evals are the gate

GraderUse forRule
CodeLabels, schema, exact match, testsFastest, most reliable
LLM judgeFaithfulness, tone, rubricRubric · reason then score · validate vs. humans · different prompt/model
HumanCalibrate judge, spot checksGold; avoid at scale
  • Criteria: specific, measurable, achievable, relevant. Volume over hand-graded perfection. Held-out set
  • Agents: start with 20–50 real failures. pass^k: 75% per run × 3 runs ≈ 42%
  • Stages: offline → CI regression → online sampled judging

Diagnose from what changed

TriggerLook at
After document refreshRetrieval / indexing
Fabricated specifics, retrieval fineHallucination: ground, cite, "I don't know"
Rule ignored on some inputsPrompt: examples, structured outputs
Smaller model, one category failsModel mismatch: route that category
Newer model, format driftsPrompt tuned to old model: re-run evals
Cost spike after deployCache hit rate (prefix changed)

A/B testing

Hypothesis · one variable · primary + guardrail metrics · sample size up front · report effect size, don't overclaim. Offline evals before online tests. +2 points on 60 samples is noise.

Optimize cost per completed task

Caching (input + TTFT) · Batch API 50% (async, ≤ 24 h, 100k requests / 256 MB, not ZDR) · routing · effort · output length (output = 5× input price) · streaming = perceived latency only. Include retries and rework.

Governance, Safety & Risk Management

14% · ~9 items · Lesson 05

  3. Apply human-in-the-loop validation

The safety stack (fails closed)

InputInjection/jailbreak screen (fast Haiku), PII redactionModel + rules

Training reduces harm; the app enforces your rules. Indirect injection: untrusted content in tool_result, screen tool outputs, limit what a hijacked agent can do ("no browser agent is immune").

Human-in-the-loop routing

Reversible, low costIrreversible / high cost
High conf.Automate + sampleApproval first
Low conf.Review queueHuman decides

Calibrate on labeled data, not self-reported confidence. Usage Policy high-risk areas need qualified human review + AI disclosure (expanded to 11 areas from Nov 12, 2026; "wholly favorable" decisions exempt).

Compliance: obligation → control → owner → evidence

  • GDPR: minimize before the call, residency/transfer + DPA, retention limits, human review of legal-effect decisions
  • HIPAA: BAA before PHI; HIPAA readiness is permanent; Managed Agents and Claude Code not covered; no PHI in schemas
  • FedRAMP High: Bedrock in AWS GovCloud (also IL4/5) or Vertex AI
  • ZDR not for: Batch, Files API, Skills, code execution, MCP connector, Managed Agents

Failure modes and fairness

  • Hallucination · prompt injection · excessive agency · over-refusal (measure false-refusal rate) · data leakage · sycophancy · cascading agent errors
  • Refusals return HTTP 200 with stop_reason: "refusal"
  • Fairness: proxies survive column deletion. Measure outcomes by group
  • Transparency for users, regulators, and your debugging team

D4 + D5 traps

Model swap without evals · unvalidated judge · winner declared on a tiny sample · per-token cost thinking · Batch for live users · rule in the prompt only · fail open when a screen is down · self-rated confidence as router · "fair because we removed gender."

D6

Stakeholder Communication & Lifecycle

14% · ~9 items · Lesson 06
Objectives
  1. Structured discovery and requirements
  2. Communicate decisions and trade-offs
  3. Feedback loops and expectations (incl. SLAs)
  4. Document architectures; implementation guidance
  5. Lifecycle: discovery, design, handoff, monitoring, iteration

Discovery

Process + baseline, volume, latency tolerance, cost of a wrong answer, reversibility, data location and sensitivity, regulatory and procurement constraints, the metric. Write assumptions down. Never open with technology.

Approval

Each option: cost · risk · reversal, in business terms. A recommendation and what would change your mind. Record it in an ADR.

Handoff

Diagrams, ADRs, prompt/config registry, eval suite + thresholds, runbooks (symptom → action → owner), named owners. Test: the team ships and rolls back without you.

SLAs and loops

  • Measured: p95 latency, quality floor on sampled review, availability, cost ceiling
  • Fallback when degraded; breach → owner + deadline
  • Iterate on local failures; re-architect on structural ones
  • Never promise "always correct"

Lifecycle

  • Deprecation: ≥ 60 days' notice; Bedrock/Google set own dates → eval successor, re-baseline cost/latency, migrate before retirement
  • Pilot: business-critical but low risk; agree graduation criteria (performance, operations, risk)
  • "Must run in our AWS" → Bedrock first

Process

  1. Read the last sentence first
  2. Find the trigger or constraint
  3. Predict, then read options
  4. Label each wrong option with a pattern
  5. Pace: item 21 @ 40 min, 42 @ 80, 63 @ 110
  6. Flag > 2.5 min; never leave blanks
  7. Multiple-response: each option true/false; assume all-or-nothing
